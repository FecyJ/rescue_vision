# 电脑端 PyQt 客户端交接

本文面向后续实现电脑端客户端的开发者，给出首版范围、现有接口、线程模型、
手柄控制、采集操作、安全约束和验收顺序。协议细节以
[`communication` 模块说明](../src/rescue_vision/communication/README.md)
和实际代码为准；电控串口命令以
《Rescue Car v2.0 — 电控代码使用说明书》及后续固件实测为准。

## 1. 目标与当前边界

首版客户端建议使用 **PyQt6**，服务于有人监督的数据采集和联调：

- 连接树莓派认证远程端点，显示连接、权限和故障状态；
- 用手柄控制前后速度和转向角速度，键盘只作调试回退；
- 通过死手按键持续授权运动，松开、失焦、手柄断开或链路异常立即进入停车
  流程；
- 发送开始录制、停止录制、抓拍和事件标记；
- 实时显示车端回传图像，并为地图、车辆状态和录制状态保留面板接口；
- 在 `observe_only` 下只观察，不显示或启用任何可发送控制的交互。

以下能力**尚未实现**，不能由客户端界面假装已经可用：

- 树莓派侧远程运动意图到底盘双轮速度的适配；
- Rescue Car UART 命令/回复/遥测解析和固件失联看门狗；
- 车端 JPEG 编码发布、地图快照、车辆状态和录制状态发布；
- IMU、定位和可靠的目标朝向控制；
- 电脑端 PyQt 应用本身及手柄后端。

首版不依赖建图、定位、正式目标模型或规划。地图面板可以先隐藏或显示
“数据源未实现”，不能用空白画面冒充有效地图。

## 2. 推荐技术选择

| 层 | 首版选择 | 边界 |
| --- | --- | --- |
| GUI | PyQt6 | 只负责视图、交互和 Qt 生命周期 |
| 手柄 | SDL 兼容后端，建议先用 `pygame` | 经 `GamepadSource` 边界输出标准化采样，不向 GUI 暴露品牌键位 |
| 网络 | 现有 `RemoteConfig.connect_client()` | 不在客户端另写 socket、认证或重连协议 |
| 控制消息 | 现有 `DebugMotionCommand` | 客户端不直接生成 UART 字符串或左右轮速 |
| 采集消息 | 现有 `DebugCaptureCommand` | 车端决定保存根目录，电脑不能传任意路径 |
| 图像 | `observation/video/frame` | 后台解码，GUI 线程只接收可显示图像 |

建议未来把 GUI/手柄依赖放入单独的 `desktop` 可选依赖组，避免树莓派最小
运行环境和无 GUI 测试被迫安装 Qt、SDL。具体版本应在开始实现时按 Python
3.13 和目标电脑系统验证后锁定；当前 `pyproject.toml` 尚未声明这些依赖。

不要直接依赖 Qt Gamepad：它不应成为业务层契约，而且不同 Qt/Python
发行组合的可用性不同。手柄实现只要满足统一采样接口，后续可替换为其他
SDL、Windows 或 Linux 后端。

## 3. 数据流与职责

```text
手柄/键盘 ─> 标准化输入 ─> 死区/曲线/限幅 ─> DebugMotionCommand
                                      │                 │
                                      │                 ▼
                                      │          认证远程连接
                                      │                 │
                                      │                 ▼
                                      │     树莓派车端适配（待实现）
                                      │                 │
                                      │                 ▼
                                      └────停车状态 <─ UART/STM32

PyQt 界面 <─ 最新显示帧/状态 <─ 观察消息分发 <─ 认证远程连接 <─ 树莓派
```

关键责任边界：

- 电脑端将操作者输入转换成车体速度意图，不计算左右轮速度；
- 车端适配器负责运动学、车体限速、UART 编码、回复/遥测解复用和最终停车；
- STM32 看门狗必须是失联停车的最后权威，网络上的“停止”消息不能替代它；
- 图传、日志和显示均为有界旁路，不得反压相机实时路径；
- GUI 不持有串口、相机或 Hailo 对象。

## 4. 可直接复用的现有接口

电脑端应只从公开包导入：

```python
from rescue_vision.communication import (
    CaptureAction,
    DebugCaptureCommand,
    DebugMotionCommand,
    MotionControlMode,
    RemoteAuthenticationError,
    RemoteDisconnectedError,
    RemoteError,
    RemotePolicyError,
    RemoteQueueOverflowError,
    RemoteTopic,
)
from rescue_vision.config import load_runtime_config
```

连接装配和生命周期：

```python
config = load_runtime_config("configs/runtime.yaml")
connection = config.remote.connect_client()
if connection is None:
    raise RuntimeError("电脑端 runtime.yaml 必须启用 remote")

# connect_client() 已完成 TCP 连接和认证；进入上下文才启动收发线程。
with connection:
    message = connection.receive_observation(timeout=0.2)
    print(message.topic, message.sequence, message.received_timestamp_ns)
```

`RemoteMessageConnection` 已有独立网络读写线程，但
`receive_observation()` 仍是阻塞调用，不能在 Qt GUI 线程中调用。
连接一旦 `stop()` 就不能再次启动；重连必须重新调用
`config.remote.connect_client()` 创建新对象。

`ReceivedRemoteMessage` 提供：

- `topic`、`content_type`、`attributes` 和原始 `payload`；
- 连接内线路序号 `sequence`；
- 发送端单调时间 `sender_timestamp_ns`；
- 电脑本机收到完整消息时的 `received_timestamp_ns`。

两台机器的单调时钟不可直接相减。端到端延迟需要额外时钟同步或车端回显
测量，不能用两个 `*_timestamp_ns` 直接计算。

## 5. 电脑端运行配置

电脑端仍需从完整的 schema v6 模板创建配置，不能只写一个 `remote` 片段：

```bash
cp configs/runtime.example.yaml configs/runtime.yaml
```

然后至少修改：

```yaml
remote:
  enabled: true
  role: client
  host: 192.168.1.20       # 树莓派在受控局域网中的地址
  port: 8765
  access_mode: debug_control
  authentication_key_path: /本机安全位置/remote.key
  handshake_timeout_ms: 2000.0
  io_timeout_ms: 100.0
  control_queue_capacity: 32
  observation_queue_capacity: 2
  max_header_bytes: 4096
  max_payload_bytes: 2097152
```

两端密钥内容必须相同，且为至少 32 字节的原始内容或 64 位十六进制文本。
密钥、实际 `runtime.yaml` 和本机路径均不得提交 Git。当前协议提供身份认证
和完整性校验，**不加密内容**；只能运行在团队受控网络或额外 VPN 内，不能
直接暴露到公网。

正式比赛配置必须为 `observe_only`。比赛运行期间规则不允许通过电脑遥控；
`debug_control` 只用于赛外采集或明确允许的调试。GUI 不能在运行中提供
“切换为调试权限”的按钮，权限只能来自启动配置和认证连接。

后续实现客户端专属配置时，至少还需版本化加入：

- 手柄设备选择或 GUID、轴/按键映射、反向、死区和响应曲线；
- 最大线速度、最大角速度、控制发送周期和命令有效期；
- 图像显示尺寸、解码开关和统计窗口；
- 键盘回退是否启用；
- 自动重连策略。

这些参数在 schema 落地前不要散落为窗口类常量。电脑端限幅只是第一层，
车端适配和 STM32 仍需独立硬限幅。

## 6. PyQt 线程与状态模型

建议将窗口状态收敛为：

```text
DISCONNECTED → CONNECTING → OBSERVE_ONLY_CONNECTED
                         └→ DEBUG_CONNECTED
任意已连接状态 ──────────→ FAULT → DISCONNECTED
```

`DEBUG_CONNECTED` 只表示远程连接允许提交控制，不表示底盘已准备好。后续
车辆状态契约应另外给出 `control_ready`、急停/看门狗状态和最近应用的命令
标识；在这些字段冻结前，界面必须保守显示“车端执行状态未知”。

推荐线程分工：

1. GUI 线程只创建控件、处理信号和绘制最后一帧。
2. 远程会话 `QObject` 移入专用 `QThread`，该线程创建、进入并关闭连接，
   循环用短超时接收观察消息，再以 queued signal 发送到 GUI。
3. 手柄后端在其初始化线程中轮询 SDL 事件，输出不可变 `GamepadSample`；
   不从 GUI 各控件直接读取原始轴。
4. 纯逻辑控制器消费最新采样，执行死区、曲线、限幅和失联判断，并按配置
   周期产生 `DebugMotionCommand`。
5. JPEG 解码不得阻塞 GUI；解码器只保留最新待显示帧。`QImage` 的底层
   缓冲区生命周期必须明确，跨线程发送前应复制或拥有独立存储。

所有跨线程 UI 更新使用 Qt signal/slot。退出顺序为：禁止新输入、尝试发送
停止、停止控制定时器、关闭远程连接、停止手柄线程、等待工作线程退出，
最后销毁窗口。即使其中一步异常，也要继续执行后续清理。

### 建议窗口布局

```text
┌ 连接地址 / 权限 / 连接按钮 ─────────────── 链路状态 / 图像年龄 / 故障 ┐
├───────────────────────────────┬─────────────────────────────────┤
│                               │ 车辆状态                         │
│        最新相机画面            │ - 控制是否就绪 / 急停 / 看门狗    │
│                               │ - 目标与实测左右轮速              │
│                               ├─────────────────────────────────┤
│                               │ 地图（数据源未实现时明确禁用）     │
├───────────────────────────────┴─────────────────────────────────┤
│ 手柄：设备 / 新鲜度 / 死手 / 线速度 / 角速度 / 输出限幅           │
├─────────────────────────────────────────────────────────────────┤
│ 录制：会话 tags / 开始 / 停止 / 抓拍 / 事件标签 / 帧数 / 磁盘告警 │
└─────────────────────────────────────────────────────────────────┘
```

连接区只展示运行配置并触发连接，不回写密钥或在日志显示密钥。运动区必须
同时显示原始手柄值和最终限幅后的速度，便于发现轴反向、漂移和映射错误。
只观察模式下保留状态与图像区域，整个运动/采集控制区禁用；不能只把按钮
变灰而让快捷键或手柄后台继续发送。

## 7. 手柄控制契约

首版只开放 `MotionControlMode.TWIST`：

- `linear_velocity_m_s > 0` 为前进，`< 0` 为后退；
- `angular_velocity_rad_s > 0` 为逆时针转向；
- `TARGET_HEADING` 在 IMU/定位和车端朝向控制器完成前必须禁用；
- 手柄映射配置决定哪根轴对应线速度和角速度，不在业务代码中写死品牌按钮
  编号。

推荐默认交互语义可以是“左摇杆纵轴控制前后、右摇杆横轴控制转向、肩键
作为死手”，但必须允许配置。轴处理顺序固定为：

```text
原始轴 → 校准中心/方向 → 死区 → 响应曲线 → [-1, 1] 限幅
      → 乘电脑端速度上限 → 形成车体速度意图
```

死手是持续状态，不是点击切换：

- 只有死手按住、手柄采样新鲜、窗口处于允许控制状态且连接健康时才发送
  非零运动命令；
- 松开死手必须立即把本地目标清零，并提交一条
  `deadman_enabled=False` 的零速度命令；
- 手柄拔出、采样过期、窗口失焦、系统休眠、连接异常、控制队列溢出和应用
  退出都走同一停车路径；
- 恢复连接或手柄后不能自动恢复上一次非零速度，必须先观察到死手释放，
  再由操作者重新按下；
- 控制发送周期与 `valid_for_ms` 必须配置化，并在真机上根据网络抖动和
  STM32 看门狗验证；schema 只允许 `valid_for_ms` 为 1～5000 ms，这不是
  安全默认值。

发送一个运动意图：

```python
import time
import uuid

from rescue_vision.communication import (
    DebugMotionCommand,
    MotionControlMode,
    RemoteTopic,
)

command = DebugMotionCommand(
    command_id=str(uuid.uuid4()),
    issued_timestamp_ns=time.monotonic_ns(),
    valid_for_ms=control_valid_for_ms,  # 来自未来的版本化客户端配置
    deadman_enabled=True,
    control_mode=MotionControlMode.TWIST,
    linear_velocity_m_s=linear_velocity_m_s,
    angular_velocity_rad_s=angular_velocity_rad_s,
)
connection.send_control(
    RemoteTopic.DEBUG_MOTION.value,
    command.to_payload(),
)
```

发送死手释放：

```python
stop = DebugMotionCommand(
    command_id=str(uuid.uuid4()),
    issued_timestamp_ns=time.monotonic_ns(),
    valid_for_ms=control_valid_for_ms,
    deadman_enabled=False,
    control_mode=MotionControlMode.TWIST,
    linear_velocity_m_s=0.0,
    angular_velocity_rad_s=0.0,
)
connection.send_control(RemoteTopic.DEBUG_MOTION.value, stop.to_payload())
```

`issued_timestamp_ns` 只供电脑侧追踪。树莓派必须从消息的
`received_timestamp_ns` 起算有效期，不能拿电脑时钟与树莓派时钟比较。
`send_control()` 成功只代表消息进入本机发送队列，不代表 STM32 已执行；
后续车辆状态应回显最近接收/应用的 `command_id`。

键盘回退也必须经过同一个纯逻辑控制器、限幅和停车路径，不能另写一套发送
逻辑。文本框、菜单或快捷键获得焦点时应禁用键盘运动控制。

## 8. 采集控制

已有控制动作：

- `CaptureAction.START`：开始一个车端录制会话，可带 `session_tags`；
- `CaptureAction.STOP`：停止当前录制；
- `CaptureAction.SNAPSHOT`：抓拍；
- `CaptureAction.MARK_EVENT`：给当前会话添加带 `label` 的事件标记。

示例：

```python
import time
import uuid

from rescue_vision.communication import (
    CaptureAction,
    DebugCaptureCommand,
    RemoteTopic,
)

request = DebugCaptureCommand(
    request_id=str(uuid.uuid4()),
    issued_timestamp_ns=time.monotonic_ns(),
    action=CaptureAction.START,
    session_tags={
        "lighting": "indoor_bright",
        "surface": "competition_like",
    },
)
connection.send_control(
    RemoteTopic.DEBUG_CAPTURE.value,
    request.to_payload(),
)
```

界面至少提供录制开始/停止、抓拍、事件标签输入及当前状态。建议允许把常用
抓拍或事件标记绑定到手柄按钮，但开始/停止录制应避免单次误触，可使用长按
或确认反馈。远端输入不能携带输出目录；车端继续从运行配置选择记录根目录，
并执行 `FrameRecorder` 的不覆盖和完整性规则。

`send_control()` 不等于录制成功。只有收到未来
`observation/capture/status` 中与 `request_id` 对应的结果后，按钮和状态栏
才能显示成功。该状态载荷尚未冻结，实现客户端前应与车端一起定义版本化
schema，至少包含：

- `request_id`、录制状态和车端接收时间；
- `recording_id`、已记录帧数、丢帧数；
- 停止或失败原因；
- 剩余磁盘空间告警。

## 9. 观察消息与界面消费

| topic | 当前状态 | 客户端处理 |
| --- | --- | --- |
| `observation/video/frame` | 通道已预留，车端发布未实现 | 校验类型和尺寸后后台解码，只显示最新帧 |
| `observation/map/snapshot` | topic 已预留，载荷未冻结 | 按版本/坐标系分发；未知版本拒绝渲染 |
| `observation/vehicle/state` | topic 已预留，载荷未冻结 | 后续显示轮速、IMU、执行/安全状态 |
| `observation/capture/status` | topic 已预留，载荷未冻结 | 将请求与车端结果关联 |

视频建议使用 `content_type="image/jpeg"`，并要求 attributes 至少包含
`frame_sequence`、`timestamp_ns`、`width`、`height` 和
`coordinate_system`。这些字段目前只是模块文档中的发布约定，尚无独立
版本化 dataclass；正式客户端不得盲目信任它们，应校验：

- topic 和 `content_type` 是否匹配；
- payload、宽高和像素上限是否在配置允许范围内；
- 解码结果尺寸是否等于声明尺寸；
- 坐标系是否为客户端支持的显式值；
- 帧号、采集时间和接收时间是否倒退或异常。

观察队列采用丢旧保新。GUI 消费到的 `sequence` 或视频
`frame_sequence` 出现跳号可以是正常背压结果，应累计并显示丢弃统计，
不能因此断开连接。控制队列不同：溢出是显式故障，必须停车并禁止继续控制。

地图、车辆状态和录制状态不得先用临时 JSON 悄悄固化。应先各自定义带
`schema_version` 的严格数据结构、无硬件测试和相邻文档，再接 GUI。

## 10. 与 Rescue Car v2.0 电控的对接点

现有说明书给出的 UART 为 115200、8N1、CRLF 行结尾，主要命令包括：

- `m<L>,<R>`：设置左右轮目标速度，单位 m/s；
- `b<L>,<R>`：柔和刹车到目标速度；
- `e`：急停；
- `v`：查询状态；
- `t<ms>,...`：约 10 Hz 自动轮速/目标速度/舵机遥测；
- `OK ...` / `ERR: ...`：命令结果。

这些内容属于后续树莓派 `car_protocol` 适配器，不属于 PyQt 客户端。适配器
应在一个 UART 接收入口统一解复用 `t`、`OK`、`ERR` 和未知前缀，不能采用
“发一条命令后读下一行就是回复”的同步假设。车体线速度/角速度到左右轮速
还依赖轮距、轮径、极性和实车限速，必须配置化并在机械参数冻结后验证。

说明书当前没有给出明确的“超过多久未收到命令即自动停车”契约。因此在
STM32 固件增加并实测失联看门狗前，只允许架空轮或有物理急停、人员全程
监督的低速调试。仅靠 PyQt 死手、TCP 断开或树莓派进程退出不能关闭这一
安全缺口。

## 11. 异常处理和重连

| 异常/事件 | 客户端动作 |
| --- | --- |
| `TimeoutError` | 短轮询无消息可视为正常；结合最后消息时间更新“数据陈旧” |
| `RemoteAuthenticationError` | 停止重试风暴，提示核对密钥，不打印密钥 |
| `RemotePolicyError` | 立即禁用控制；通常表示 `observe_only` 或两端权限不一致 |
| `RemoteQueueOverflowError` | 控制链路故障，进入停车流程并要求人工重新使能 |
| `RemoteDisconnectedError` | 本地目标清零、禁用控制、关闭旧连接后按退避重连 |
| `RemoteError` / socket 错误 | 记录非敏感错误，清理资源并进入 `FAULT` |
| 手柄断开/采样超时 | 与死手释放相同，但恢复后要求重新按下死手 |
| JPEG/状态载荷错误 | 丢弃该观察消息并计数；连续错误升级为观察流故障 |

自动重连只能恢复观察链路，不能自动恢复运动。重连采用有上限的指数退避和
随机抖动；关闭窗口时必须能中断退避。认证失败和配置错误应等待人工修改，
不应无限快速重试。

## 12. 建议代码位置

开始实现且同时加入真实代码和测试时，可在 `src/rescue_vision/` 下新增一个
职责明确的 `desktop/` 包；在此之前不要创建空目录。建议边界：

```text
desktop/
├── README.md              # 公共入口、配置、生命周期和人工验收
├── app.py                 # 参数解析、配置加载和 Qt 对象装配
├── main_window.py         # 窗口和展示，不包含网络/运动学
├── remote_session.py      # QThread 中的连接生命周期、重连和消息分发
├── gamepad.py             # GamepadSource、SDL 实现和标准化采样
├── drive_control.py       # 死区、曲线、死手、限幅和命令生成纯逻辑
├── capture_control.py     # 录制请求与状态关联纯逻辑
└── observation_decode.py  # 视频及未来版本化状态载荷校验
```

不要为每个控件拆文件，也不要创建通用 `utils.py` 或空的适配器树。Qt 之外
的控制规则保持纯 Python，保证无显示器、无手柄、无网络也能 pytest。

建议增加命令 `rescue-vision-desktop --config configs/runtime.yaml`。CLI
只解析参数、加载配置并创建 `QApplication`，不能在导入模块时连接网络、
初始化 SDL 或创建窗口。

## 13. 实现顺序

1. 增加版本化桌面/手柄配置和纯逻辑 `GamepadSample`、轴处理、死手状态机；
   先用 pytest 覆盖死区、反向、限幅、断连和重新使能。
2. 实现 PyQt 只观察客户端：连接状态、后台收包、JPEG 最新帧显示、统计和
   干净退出；先与合成发布端联调。
3. 冻结 STM32 失联看门狗和车端运动适配，完成架空轮验证后再启用 GUI
   `debug_control`。
4. 接入 SDL 手柄和键盘回退，验证失焦、拔线、休眠、网络断开、进程退出和
   控制队列溢出的停车路径。
5. 接入车端录制命令与版本化状态回执，再开放手柄采集快捷键。
6. 冻结并接入车辆状态；地图只在真实坐标和 schema 可用后实现。
7. 最后进行双机吞吐、延迟、长时间运行和整车低速采集验收。

## 14. 验收清单

无硬件 pytest 至少覆盖：

- 不同手柄原始轴映射到相同标准化方向；
- 中心漂移处于死区时速度严格为零；
- 输出有限、限幅正确，NaN/Inf 和非法配置被拒绝；
- 未按死手、采样过期、手柄断开和重新连接时不能产生非零命令；
- `observe_only` 中所有控制入口均禁用，底层发送仍会被策略拒绝；
- 控制命令和采集命令 round-trip 使用现有 schema；
- 观察分发按 topic/content type/schema 严格校验；
- 图像突发只保留最新帧，控制队列溢出不被吞掉；
- 重连不会复用已关闭连接，也不会恢复旧速度；
- Qt 模块导入不连接网络、不初始化手柄、不创建窗口。

电脑人工验收至少覆盖：

- 无手柄启动、运行中插拔、多个手柄选择和轴/按钮校准；
- 窗口失焦、最小化、关闭、系统休眠与恢复；
- 错误密钥、树莓派未启动、网络抖动、断网和服务端重启；
- 不同分辨率 JPEG、坏帧、超大帧和高帧率下 UI 不冻结；
- `observe_only` 与 `debug_control` 的界面和底层双重权限。

真车验收必须在固件看门狗完成后，先架空轮再低速落地，逐项断开手柄、TCP、
UART、相机和树莓派进程，并确认由 STM32 在约定时间内停车。记录目标硬件
端到端控制延迟、图像年龄、丢帧率、CPU/内存和连续运行时间；只报告 GUI
刷新率或网络吞吐不算完成。

现有观察链路可先用以下命令做双机认证检查：

```bash
python manual_tests/remote_link.py \
  --config configs/runtime.yaml \
  --timeout-seconds 10
```

它只验证一条观察消息往返，不验证图传吞吐、手柄控制或失联停车。
