# 项目结构

本页只回答两个问题：一个功能现在在哪里，以及新代码应该放在哪里。实现状态以 [README](../README.md) 为准，任务顺序以 [后续优先级](后续优先级.md) 为准。

## 当前目录

```text
rescue_vision/
├── configs/runtime.example.yaml       # 唯一运行配置示例
├── docs/                              # 规则、路线图和专项操作文档
├── examples/                          # 明确标为合成的 schema 夹具
├── manual_tests/                      # 真机和 GUI 人工验收
├── src/rescue_vision/
│   ├── calibration/                  # 标定采集与求解命令
│   ├── camera/                       # 帧、真机源、回放、记录
│   ├── config/                       # 运行配置加载与装配
│   ├── data/                         # 数据清单和划分命令
│   ├── evaluation/                   # 离线指标与报告命令
│   ├── geometry/                     # 坐标、去畸变、地面投影
│   └── versioning.py                 # 记录 Git 版本与 dirty 状态
└── tests/                            # 无硬件 pytest
```

没有 `perception/`、`tracking/`、`localization/`、`world/`、`mission/`、`interfaces/` 或 `app.py`，因为这些能力尚未实现。规划中的名称不提前创建为空目录。

每个已实现包的最简调用代码见 [`src/rescue_vision/README.md`](../src/rescue_vision/README.md)，再由该页进入对应包 README。

## 文件定位表

| 责任 | 权威文件 |
| --- | --- |
| 帧数据和统一帧源协议 | `camera/frame.py` |
| `rpicam-vid` 最新帧源 | `camera/rpicam_source.py` |
| Picamera2 最新帧源及传感器元数据 | `camera/picamera2_source.py` |
| 图片、视频、记录目录回放 | `camera/replay.py` |
| 异步记录目录格式 | `camera/recording.py` |
| 录制命令 | `camera/record_cli.py` |
| 严格 YAML 配置 | `config/runtime.py` |
| 相机模型与去畸变 | `geometry/camera_model.py` |
| 像素、地面和 BEV 坐标类型 | `geometry/types.py` |
| 地面映射 | `geometry/ground_projector.py` |
| 记录转数据清单 | `data/build_manifest.py` |
| 防泄漏数据划分 | `data/split_manifest.py` |
| 指标计算 | `evaluation/report.py` |
| 评测命令薄封装 | `evaluation/cli.py` |

标定的三个脚本按完整工作流组织，虽然较长，但每个脚本各自只有一个操作入口。除非其中出现可被多个运行模块复用的稳定算法，否则不为了缩短文件而拆成更多跳转层。

## 模块边界

```text
Camera Frame
    │
    ├── CameraModel ──> 去畸变帧/点
    │                       │
    │                       └── GroundProjector ──> GroundPoint / BevPixel
    │
    └── Recorder（旁路）──> RecordingSource ──> 离线回放
```

- `camera` 只负责帧的产生、生命周期、回放和原始记录，不做识别或坐标变换。
- `geometry` 不创建相机，也不解释比赛类别。
- 未来的检测器消费 `FrameSource` 和显式配置，只输出带帧号、时间、坐标系、置信度和质量标记的观测。
- 跟踪、定位、世界模型与规则状态机消费观测；检测器不得直接修改它们。
- 电控、Hailo 和串口通过可替换后端接入，不能侵入算法模块。

推荐主链路：

```text
FrameSource
  → CameraFrame
  → CameraModel
  → Perception
  → Tracking / Localization
  → WorldModel
  → Mission
  → Interfaces
```

只允许已实现的层出现在 README “已实现”状态中。

## 坐标与时间

```text
RawPixel → UndistortedPixel → GroundPoint ↔ BevPixel
                                  │
                                  └── FieldPoint（全局定义冻结后使用）
```

- 像素：`u` 向右、`v` 向下；图像尺寸顺序为 `(width, height)`。
- 机器人地面：`x` 向前、`y` 向左、`z` 向上，单位 mm。
- BEV：上方对应机器人前方，左侧对应机器人左方。
- `timestamp_ns` 是应用收到完整帧时的单调时间；Picamera2 的传感器时间另存于元数据。
- 任何跨模块坐标都要能确定坐标系、单位、帧号和时间基准。

## 新代码放置规则

新增目录前同时满足：

1. 有可运行实现，而不是只有接口占位或未来计划。
2. 责任无法自然归入现有目录。
3. 有无硬件测试，或明确列入人工验收。
4. README 状态和本页定位表同步更新。

一个具体职责优先使用一个模块；不要为单个小文件建立新的顶层包。CLI 只解析参数和调用领域函数，业务校验留在可测试模块。内部 API 尚未发布时，直接更新所有调用方，不保留无用途的兼容包装。

未来落地时建议按以下顺序增长，而不是一次性创建整棵目录树：

1. `perception/`：首个检测器与统一观测真实落地时创建。
2. `tracking/`、`world/`、`mission/`：相应纯逻辑实现与测试落地时分别创建。
3. `localization/`：场地坐标和视觉位姿观测实现时创建。
4. `interfaces/`：通信 mock 与版本化消息实现时创建。
5. `app.py`：至少两层主链路能够装配运行时创建。

## 实时与测试边界

- 采集线程持续排空输入，只保存最新帧。
- 去畸变每帧最多一次；完整 BEV 仅按需生成并在同帧复用。
- 录像、可视化、日志和通信不得用无界队列阻塞实时路径。
- `tests/` 只能包含开发机可执行的自动测试。
- `manual_tests/` 承载相机、Hailo、GUI、固定安装和整车验收；脚本必须自行释放资源。
