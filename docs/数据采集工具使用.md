# 数据采集工具使用手册

本页是相机采集的唯一操作手册，覆盖“相机预检 → 短录冒烟测试 → 正式分会话录制 → 完整性验收 → 数据清单 → 防泄漏划分”。记录目录和 JSONL 字段定义见[数据集与评测 schema](数据集与评测.md)。

当前工具只负责原始帧、会话标签、完整性和数据版本组织，不会自动生成目标框或 K0 标注。实际数据资产不应提交 Git。

最短路径：安装项目并复制配置 → 用 `rpicam-hello` 预检 → `rescue-vision-record` 短录 → `rescue-vision-check-recording` 验收 → 按“正式采集覆盖”分会话录制 → 生成 manifest 和 split。

## 1. 安装和工作目录

在仓库根目录安装可编辑包，确保后续命令指向当前代码：

```bash
source .venv/bin/activate
python -m pip install -e .
```

建议把采集资产放在容量充足、不会被 Git 跟踪的独立目录。下文统一使用仓库外的 `/data/rescue-targets` 作为示例；请按实际挂载点替换：

```text
/data/rescue-targets/
├── recordings/                 # 原始、不可变的记录会话
├── reports/                    # 单会话检查与划分报告
└── manifests/                  # 数据集 JSONL
```

录制前检查剩余空间：

```bash
df -h /data/rescue-targets
```

图片体积随画面内容变化，不能只按理论帧率估算。先做 10 秒冒烟录制，以实际目录大小推算当天所需空间。

## 2. 准备采集配置

从模板复制本机配置，`configs/runtime.yaml` 不提交：

```bash
cp configs/runtime.example.yaml configs/runtime.yaml
```

采集阶段重点核对：

```yaml
camera:
  backend: picamera2
  image_size: [2304, 1296]
  fps: 20
  lens_position: 1.0

geometry:
  enabled: false

recording:
  queue_capacity: 8
  image_format: jpg
```

- 正式采集优先使用 `picamera2`，因为它会保存传感器时间、曝光、增益、白平衡和焦点等逐帧元数据。
- `image_size` 顺序是 `[width, height]`。
- 固定焦点后记录实际 `lens_position`；改变分辨率、裁剪、焦点或安装状态会改变标定适用范围。
- 2304×1296、20 FPS 默认使用质量 95 的 `jpg`。本机实测 PNG 编码明显跟不上实时写入；只有降低帧率并通过短录门禁后才使用 `png`。两种格式不能在同一数据版本内无说明地混用。
- 数据采集不依赖地面投影时可以关闭 `geometry`，避免本机尚未完成的地面标定阻塞原始数据录制。

先验证配置能够严格加载：

```bash
python -c "from rescue_vision.config.runtime import load_runtime_config; print(load_runtime_config('configs/runtime.yaml'))"
```

## 3. 相机预检

确认系统能枚举相机：

```bash
rpicam-hello --list-cameras
```

若使用桌面环境，可分别运行：

```bash
python manual_tests/picamera_minimal.py
python manual_tests/camera_stream.py
```

检查画面方向、视野、焦点、曝光是否稳定，并确认没有遮挡保护罩边缘。无桌面环境时可以跳过预览，直接做下一节短录并抽查保存图片。

`rpicam-hello` 报 `No cameras available` 时不要继续采集。依次检查排线方向、相机是否被其他进程占用、DMA heap/设备权限和系统相机配置。

## 4. 做一次短录冒烟测试

每次更换相机、存储介质、分辨率、焦点或系统镜像后，先录制一个新的测试目录：

```bash
rescue-vision-record \
  --config configs/runtime.yaml \
  --output /data/rescue-targets/recordings/smoke_20260723_001 \
  --frames 200 \
  --tag lighting=indoor_bright \
  --tag distance=near \
  --tag occlusion=none \
  --tag motion_blur=low \
  --tag background=official_mat \
  --tag target_pose=upright \
  --tag contact_state=isolated
```

`--frames` 表示从最新帧源交付多少帧后停止，不保证全部写盘；记录队列满时会丢弃旁路写盘请求，并在统计中体现。也可以按时长录制：

```bash
rescue-vision-record \
  --config configs/runtime.yaml \
  --output /data/rescue-targets/recordings/smoke_20260723_002 \
  --duration-seconds 10 \
  --tag lighting=indoor_bright
```

`--frames` 和 `--duration-seconds` 互斥；两者都不提供时会持续录制，按 `Ctrl+C` 正常收尾。未填写的必需标签会明确保存为 `unknown`，适合设备冒烟测试，但正式资产应尽量填写真实场景标签。

输出目录必须是不存在或为空的新目录。工具不会覆盖已有会话，这是为了避免把两次物理布置混入同一个 `recording_id`。

## 5. 检查记录健康状态

对短录目录完整回放并保存报告：

```bash
rescue-vision-check-recording \
  /data/rescue-targets/recordings/smoke_20260723_001 \
  --report /data/rescue-targets/reports/smoke_20260723_001.json \
  --minimum-frames 180 \
  --maximum-drop-ratio 0.05 \
  --minimum-fps-ratio 0.80 \
  --require-picamera2-metadata
```

检查会重新读取并验证每张图片的 SHA-256 和尺寸，还会验证帧序、时间戳、记录统计，最后按显式门限返回：

- 退出码 `0`：全部门限通过，报告中 `passed` 为 `true`。
- 退出码 `1`：记录可读取，但帧数、丢帧率、有效帧率或元数据门限未通过。
- 退出码 `2`：目录、JSON、哈希、尺寸或记录结构损坏，无法完成检查。

主要报告字段：

| 字段 | 含义与判断 |
| --- | --- |
| `frame_count` | 实际通过哈希回放的图片数 |
| `effective_fps` | 由首末应用单调时间和帧数计算的平均写入帧率 |
| `drop_ratio` | 记录旁路因队列满而丢弃的比例，不是相机内部丢帧 |
| `sequence_gap_count` | 真机源跳过旧帧或记录器未接受的序号总缺口；大于 0 时检查负载 |
| `metadata_coverage` | 每个非空元数据字段覆盖了多少帧 |
| `luma.mean_*` | 灰度均值范围，用于发现全黑、严重欠曝或严重过曝 |
| `luma.stddev_*` | 帧内灰度标准差范围；长期接近 0 通常表示无纹理或异常纯色画面 |
| `failures` | 未通过门限的可操作原因 |

`--require-picamera2-metadata` 会要求传感器时间、曝光、模拟/数字增益、色温、红蓝增益、焦点和帧周期在每一帧存在。使用 `rpicam_vid` 时不要加这个选项，因为该后端不承诺逐帧传感器元数据。

`luma` 只提供诊断，不设置通用硬门限：深色目标、阴影和反光本来就是必须采集的场景。应结合抽帧目视确认，而不是因亮度统计“不漂亮”而删除困难样本。

最简抽帧检查代码：

```python
import cv2

from rescue_vision.camera.replay import RecordingSource

with RecordingSource(
    "/data/rescue-targets/recordings/smoke_20260723_001"
) as source:
    first = source.read()

cv2.imwrite("/tmp/rescue-smoke-first.png", first.image_bgr)
print(first.sequence, first.timestamp_ns, first.metadata)
```

还应直接打开会话的首、中、末帧，确认目标没有出画、运动场景确实有预期模糊、焦点正确且颜色没有明显异常。

## 正式采集覆盖

必须使用规则允许的实物，或尺寸、材质和颜色高度一致的打印件。棋盘、蓝色测试块和本页的冒烟画面不能代替四类目标数据。

采集前确认：

- [ ] 绿色 40 mm 普通物资正方体；
- [ ] 黑色 40 mm 核心物资正三棱锥；最终形态以组委会实物或图纸为准；
- [ ] 橘色 80×40×40 mm 伤员长方体；
- [ ] 浅蓝 40 mm 危险目标正方体；
- [ ] 接近正式场地的底色、安全区材料、边界和常见彩色干扰物；
- [ ] 相机为 2304×1296、固定焦点，并记录实际 `LensPosition`。

每类目标至少覆盖：

| 维度 | 建议取值 |
| --- | --- |
| 光照 | 明亮、偏暗、局部阴影、反光 |
| 距离 | 近、中、远、图像边缘 |
| 姿态 | 正立、倾倒、主要旋转方向 |
| 遮挡 | 无、轻度、明显但仍可辨认 |
| 运动 | 静止、慢速横移、快速横移或转动模糊 |
| 接触 | 孤立、同类相邻、跨类别接触、危险目标靠近普通目标 |
| 背景 | 场地材料、边界、安全区、非目标彩色干扰物 |

困难场景优先级最高：危险目标与蓝色安全区或反光材料同框、黑色核心目标处于阴影、橘色伤员部分遮挡、多个目标接触。改变任一场景维度时创建新的 `recording_id`。

## 6. 录制正式数据会话

一个会话只对应一种连续拍摄和一组固定场景标签。改变目标类别、光照、距离档位、遮挡程度、运动方式、背景或接触关系时，停止当前录制并创建新目录。

推荐命名：

```text
目标类别_关键场景_YYYYMMDD_三位序号
```

例如：

```text
blue_danger_blue_zone_shadow_20260723_001
black_core_far_motion_20260723_002
```

完整命令：

```bash
rescue-vision-record \
  --config configs/runtime.yaml \
  --output /data/rescue-targets/recordings/blue_danger_blue_zone_shadow_20260723_001 \
  --duration-seconds 20 \
  --tag lighting=partial_shadow \
  --tag distance=medium \
  --tag occlusion=light \
  --tag motion_blur=low \
  --tag background=blue_safe_zone \
  --tag target_pose=upright \
  --tag contact_state=cross_class_touching
```

标签值目前由数据负责人维护受控词表；工具严格约束标签名称，但不会擅自限制值。团队应在一次数据版本内固定英文小写值，避免同时出现 `bright`、`indoor_bright`、`明亮` 等同义值。必需标签名称是：

```text
lighting, distance, occlusion, motion_blur,
background, target_pose, contact_state
```

每个正式会话结束后立即运行 `rescue-vision-check-recording`。检查失败时保留原目录和报告用于排障，使用新的 `recording_id` 重录；不要手工把缺帧补进旧目录，也不要修改 `frames.jsonl` 或 `session.json` 伪造通过状态。

## 7. 生成数据集清单

当一批会话均通过单会话检查后，明确列出它们生成清单：

```bash
rescue-vision-manifest \
  --dataset-root /data/rescue-targets \
  --dataset-version rescue-targets-2026-07-23-v1 \
  --output /data/rescue-targets/manifests/rescue-targets-2026-07-23-v1.jsonl \
  /data/rescue-targets/recordings/green_supply_bright_20260723_001 \
  /data/rescue-targets/recordings/black_core_shadow_20260723_001 \
  /data/rescue-targets/recordings/orange_injured_occluded_20260723_001 \
  /data/rescue-targets/recordings/blue_danger_blue_zone_20260723_001
```

这里的 `--dataset-root` 必须是所有记录目录的共同资产根目录，输出的图片路径会相对它保存。命令默认再次验证全部图片哈希，并拒绝：

- 未正常结束或零帧的记录；
- 缺失必需标签；
- 重复 `recording_id` 或样本 ID；
- 非递增序号/时间戳；
- 统计数量不一致；
- 根目录之外的资产路径；
- 损坏或被替换的图片。

发布训练、验证或评测用数据版本时不要使用 `--skip-image-verification`。该选项只适合已另行验证过的大数据集本地快速迭代。

## 8. 按记录组划分

同一会话的相邻帧高度相关，必须以 `recording_id` 整组划分：

```bash
rescue-vision-split \
  /data/rescue-targets/manifests/rescue-targets-2026-07-23-v1.jsonl \
  --output /data/rescue-targets/manifests/rescue-targets-2026-07-23-v1.split.jsonl \
  --report /data/rescue-targets/reports/rescue-targets-2026-07-23-v1.split.json \
  --seed rescue-targets-2026-07-23-v1 \
  --train-ratio 0.70 \
  --validation-ratio 0.15
```

剩余比例自动作为测试集。相同输入、seed 和比例会得到相同结果。划分报告应重点检查：

- `group_counts`：三个集合是否都有足够的独立会话；
- `sample_counts`：帧数是否过度失衡；
- `tag_distribution`：危险目标、阴影、遮挡、接触和蓝色安全区干扰是否只落在单一集合。

会话数很少时，稳定哈希不保证三个集合恰好都有数据。正确做法是补录独立会话，或在数据版本冻结前统一调整 seed/比例并重新生成；不能把同一录像拆开填补空集合。

## 9. 标注与版本冻结

原始 `recordings/` 一经验收应视为只读。标注工具引用原图，标注格式遵循 [Pose 视觉模型约定](Pose视觉模型约定.md)，不要覆盖或重新编码原图。

冻结一个数据版本时至少保存：

- 原始记录目录的只读存储位置和备份位置；
- 数据集版本名；
- 未划分和已划分 JSONL；
- 单会话检查报告与划分报告；
- 使用的 Git 提交；
- 标注版本和标注检查结果；
- 已知缺口，例如尚未覆盖的背景或困难姿态。

Git 只提交工具、文档和小型合成测试夹具；不要提交批量录像、采集帧、正式标注资产或大模型权重。

P0 现场数据完成时应同时满足：

- [ ] 四类目标均有可哈希验证的实拍记录；
- [ ] 静态和手持运动会话都可由 `RecordingSource` 回放；
- [ ] 每个会话的健康检查通过，并目视抽查首、中、末帧；
- [ ] 清单通过严格 schema，划分报告中不存在会话泄漏；
- [ ] 数据版本、只读存储位置、报告和校验信息已记录。

底盘完成后的真实振动、减速带和碰撞域数据属于补充域，不阻塞当前实物数据基线。

当前 Raspberry Pi 5 + IMX708 Wide 已验证 2304×1296、20 FPS、JPEG 95 可持续写入且 Picamera2 元数据完整；该冒烟结果不含四类正式目标，不能充当数据资产或模型性能证据。

## 10. 常见问题

### 记录目录显示 `completed: false`

说明录制没有写出任何帧、进程被强制终止，或写盘线程异常。检查终端错误、磁盘空间和目录权限后，用新目录重录。不要手工改为 `true`。

### 丢帧率过高

先确认存储空间和写入性能，再减少同时运行的预览/推理任务，适当增大 `recording.queue_capacity`，或改用更快的存储介质。增大队列会增加内存占用，只能吸收短时抖动，不能修复持续写盘不足。

### 有效帧率明显低于配置

检查相机曝光是否因暗光变长、CPU/存储是否饱和、相机源是否频繁跳过旧帧。训练数据不要求每段都达到精确实时帧率，但运动域会因此改变，必须重录或明确记录差异。

### 元数据覆盖不全

先确认配置确实使用 `picamera2`。若只有个别字段缺失，记录相机型号、系统版本和缺失字段，不要伪造值；决定是否降低正式门禁前应先确认该字段在当前驱动上是否可提供。

### 哈希不匹配

原图已损坏、被覆盖或传输不完整。保留报告，尝试从只读备份恢复；无法恢复时淘汰整个受影响会话并重录，不能重新计算哈希掩盖变更。
